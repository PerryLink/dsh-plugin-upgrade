# 版本卡 · `0.1.5-alpha.1` → `0.1.5-rc.1`

> 适用：任何 `@deepseek-ai/dsh-*` peer 落在 `>=0.1.2-rc.1 <0.2.0` 且需要支持 `0.1.5-rc.1` 的插件仓（含带 client 半边的仓）。
> 状态：**已发布**（当前发布版本见本包 `package.json`；npm `dsh-plugin-upgrade-rc1` · GitHub `PerryLink/dsh-plugin-upgrade-rc1`）。
> 证据基线（2026-09-10 实测，只读）：`D:\deepseek-harness` 只读 checkout，tag `dsh-v0.1.5-alpha.1` = `5dda764ed3aa172535a7967b06ff95d9cbfe536a`、`dsh-v0.1.5-rc.1` = `183f08e9c6dde7e36cd2318eaee70b0da08fb35e`；家族工作区 `D:\Projects\dsh\plugins`。逐条命令与原始输出见本包 `docs/EVIDENCE.md`。
> 复现方式：本包 CLI `dsh-plugin-upgrade-rc1-scan --repo <仓库>` 输出 `file:line`，再按本卡逐缝处理。本卡只对 `0.1.5-alpha.1 → 0.1.5-rc.1` 负责。

## 0. 这一跳与其它跳的关系

| 项 | 值（2026-09-10 实测） |
|---|---|
| from tag / commit | `dsh-v0.1.5-alpha.1` / `5dda764ed3` |
| 中间 tag（必须知道） | `dsh-v0.1.5-alpha.2`（`alpha.1..rc.1` 共 **279** 个 commit，其中 **262** 个在 alpha.2 之前；`alpha.2..rc.1` 只有 **17** 个） |
| to tag / commit | `dsh-v0.1.5-rc.1` / `183f08e9c6` |

`alpha.2` 只是一个 17-commit 的短命 tag，没有任何家族仓钉它；把它当成走廊起点只会增加噪音。**但 279 个 commit 的绝大部分（262 个）发生在 `alpha.1 → alpha.2` 之间**，所以本卡必须同时描述这两段，否则 rc.1 独有的接缝（`present` 工具、模型目录默认值）会被漏掉。

| 走廊 | 归属 |
|---|---|
| `0.1.3-alpha.1 → 0.1.5-alpha.1` | **姊妹走廊** `dsh-plugin-upgrade`（另一张卡、另一个包）。若你的 peer 低于 `0.1.5-alpha.1`，先读它把插件送到 alpha.1，再回到本卡。 |
| `0.1.5-alpha.1 → 0.1.5-rc.1` | **本卡**。 |
| `0.1.5-rc.1 → 正式版` 及任何未来线 | 不在任何卡上：a drifting card is worse than no card。 |

两条走廊**零代码依赖**、只做交叉引用：本包不 import、不 vendor、不 vendor 姊妹包的 `SEAMS`。理由：走廊包的 `./scan` 导出携带的是**锁定的**接缝目录，复用等于把新走廊的运行时耦合到旧走廊的内容版本；而规则原文只要求"a new **package**"，没说允许把旧包改成多走廊框架（`dsh-plugin-upgrade` 的 `README.md` 明写 **One corridor only**）。

## 3. C1 · 裸 slot `conversation` 被删除（**本卡的中心接缝**）

### 3.1 上游事实（逐条实测）

同一文件同一位置，`packages/client/ui-conversation/src/client/apply.ts`：

```
dsh-v0.1.5-alpha.1:…/apply.ts:217:    name: 'conversation',
dsh-v0.1.5-rc.1:…/apply.ts:220:    name: 'main.conversation',
dsh-v0.1.5-rc.1:…/apply.ts:388:  slots.inject('main', function* () {
dsh-v0.1.5-rc.1:…/apply.ts:390:      name: 'main',
dsh-v0.1.5-rc.1:…/apply.ts:391:      key: 'conversation',
dsh-v0.1.5-rc.1:…/apply.ts:392:      children: { 'main.conversation': { kind: 'single', scope: 'session-maybe' } },
```

- 公开 slot 目录 `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` 的 `key:` 集合：alpha.1 = **57**，rc.1 = **61**。
- **删除（1 个）**：`conversation`。**新增（5 个）**：`main`、`main.conversation`、`rightbar.session`、`sidebar.panellist`、`sidebar.right.tab.document`。
- rc.1 全树搜 `name: 'conversation'`：只剩 `packages/client/ui-agent-preset/tests/apply.client.spec.ts:135` 一处**测试夹具残留**，实现侧零命中，**没有别名、没有 shim**。
- 精度：`conversation.input.left`、`conversation.session.header.actions`、`conversation.chat.node` 这些**以 `conversation.` 开头的名字本身没有变**，只有**裸 `conversation` 这一个 key** 被删除。`declaredBy` 的措辞从 `'an entry in conversation'` 变成 `'an entry in main.conversation'` 是目录描述文案。

### 3.2 失效形态是静默的（C1 必须保持 error 的理由）

rc.1 的公开 `ctx.slots` 契约（`packages/extensions/cordis-client-runner/src/client/api-catalog.ts`，`SERVICE_API` 的 `key: 'slots'`）逐字为：

> `inject(key: keyof SlotMap & string, callback: () => SlotInjectionEffect): () => void`
> "Install an effect for each declaration lifetime of a slot. The callback runs synchronously when the declaration already exists; otherwise it runs inside the declaring `register()` call after the declaration is committed."

`conversation` 在 rc.1 **永不 declaration**，所以回调**永不执行**：插件的 UI 悄悄消失，没有报错、没有日志、没有挂载失败。这与姊妹走廊最核心的洞察（`M1` 的"假绿"）是**同一类失效模式，只是从编译期搬到了运行期**。

### 3.3 本仓裁定：这是**公开扩展点的破坏性移除**，不是 owner 内部席位改名

研究稿把这留作开放问题（"公开扩展点"还是"内部席位"）。本仓采纳的裁定与理由：

**裁定：C1 是公开扩展点的破坏性移除，保持 `error` 级。**

1. `conversation` **确实出现在**两个 tag 都公开可查的 slot 目录（`slot-catalog.ts` → Inspect `Slots.listSubTree`）里，插件作者正是通过这份目录选 slot 的。
2. `ctx.slots.inject` 的公开契约明确支持"等 declaration 出现"的用法（§3.2 引文）。
3. 删除**没有别名**，rc.1 也未提供 shim 包；`conversation.` 前缀下的其它 key 全部保留，说明这不是一次体系化重命名，而是**单个 key 的移除**。
4. 上游在 `docs/` 里**没有**任何 deprecation 或 migration note：`docs/capability-seams.md` 的区间 diff 只新增了服务级 `ctx.sessionFeedback` 一行，**没有**任何 slot 级说明。**rc.1 至今没有发布这份迁移说明。**
5. 反向证据（研究稿提出的"内部席位"论据）成立但不改变结论：rc.1 的命名体系确实转向 `main.*` / `rightbar.session` 这类带父入口的点分名字。**这是动机，不是兼容性结论**——无论上游意图如何，第三方插件面对的都是"目标 key 消失 + 无别名 + 无 deprecation + 静默失效"。

**因此本卡给出完整改写配方（§3.4），并要求对每个 `C1` 命中项做真实浏览器断言（§10 第 5 步）。** 静态扫描与 `typecheck` 都不能作为 C1 已修好的证据。

### 3.4 改写配方

rc.1 的 `main` slot 目录原文（`slot-catalog.ts`）：

```
kind: 'keyed', scope: 'root',
summary: 'Central panel selected by sidebar entry id.',
doc: 'Central panel selected by sidebar entry id. The reserved `conversation` key hosts the Conversation; other keys receive no Session binding.',
keyDomain: 'open: any string the owner dispatches (no compile-time key set), already taken: conversation',
occupants: ['client-ui-conversation ConversationPanel key \'conversation\'']
```

| 你原来的意图 | 改成 | 说明 |
|---|---|---|
| 往会话内容区塞一个元素（多数插件想要的） | `ctx.slots.inject('main.conversation', () => ctx.slots.register({ name: 'main.conversation' }, Component))` | `main.conversation` 是 single / session-maybe，occupant 为官方 `ConversationRoot`；官方目录里给出的 `example` 就是这个形状 |
| 注册一个新的全局中央面板 | `ctx.slots.inject('main', () => ctx.slots.register({ name: 'main', key: '<你的 key>' }, Panel))`，并配 `sidebar.panellist`（list/root）提供入口按钮 | `key` 必填；`conversation` 这个 key 已被官方 `ConversationPanel` 占用，`register` 一个已占用的 key 会**替换**该 occupant |
| 只是想"会话存在时才挂载" | 仍然用 `main.conversation` | 它的 scope 是 `session-maybe` |

**不要**把 `inject('conversation')` 改成 `inject('conversation.session')` 之类的"就近改名"：那些 key 语义完全不同（`conversation.session` 是会话内容容器，不是插件可注册的 root 面板位）。

## 5. C3 · client 侧的假绿（结构化检测）

两类独立成因，命中任一即为 error：

1. **dev/test 依赖钉在 alpha 线**：`package.json` 的 `devDependencies` 里出现 `@deepseek-ai/*` 且 spec 是 `0.1.5-alpha.1` / `0.1.5-alpha.2`（可带 `^`/`~`）。此时本地 `typecheck` 编译的是**旧 slot 目录**，rc.1 删掉的 key 依然"合法"。
   - 刻意**不**匹配 `>=0.1.2-rc.1 <0.2.0 || >=0.1.5-alpha.1 <0.2.0` 这种仍然覆盖 rc.1 的区间，也不匹配更老的 `0.1.2-rc.1` 钉号（那是另一条走廊的事，且可能是刻意的多线测试）。
2. **`tsconfig` `paths` 解析失败**：checkout 风格的别名（指向 `packages/` / `vendor/` 或含 `deepseek-harness`）解析到一个**不存在的目录**时，TypeScript 会**静默回退**到 `node_modules` 的已发布类型。正确形状（相对仓库根）：`../../../../deepseek-harness/packages/<pkg>/lib/types/index.d.ts`。

正确做法：dev/test 依赖钉 `0.1.5-rc.1`，`paths` 目标必须存在；两条都要绿再谈其它。

## 9. P1 · peer 区间（**最容易"顺手简化"而踩雷的一行**）

用 semver **7.8.5** 实测（`satisfies('0.1.5-rc.1', range)`）：

| 区间 | `0.1.5-rc.1` 是否满足 |
|---|---|
| `>=0.1.2-rc.1 <0.2.0`（**砍掉第二段**） | **false** ❌ |
| `>=0.1.2-rc.1 <0.2.0 \|\| >=0.1.5-alpha.1 <0.2.0`（家族现行） | **true** ✅ |
| `>=0.1.5-alpha.1 <0.2.0` | **true** ✅（`0.1.5-alpha.1` 自身也 true） |

原因：npm semver 的 **prerelease-tuple 规则**——带 prerelease 的版本只有在同一 `[major,minor,patch]` 元组上**至少有一个带 prerelease 的 comparator** 时才被允许满足该集合。`>=0.1.2-rc.1` 的元组是 `0.1.2`，管不到 `0.1.5-rc.1` 的元组 `0.1.5`，于是整条被拒；第二段 `>=0.1.5-alpha.1` 的元组正是 `0.1.5` 且带 prerelease，才把它放行。

这与工作区已记录的历史事故同源（旧范围 `>=0.1.0-rc.8 <0.2.0` 因同一规则在裸解析下只匹配 `0.1.0-rc.8` 一行）。

**硬规则：rc.1 适配不改 peer 区间；绝对不要把两段"或"合并成一段。** 需要区分两件事：

- **peer 区间不动** —— 这是 `dsh-skill` 等依赖解析用的。
- **`dshWorkshop.compatibility.dshVersions` 换号** —— 市场/工坊的兼容声明：把 `0.1.5-alpha.1` **替换**为 `0.1.5-rc.1`，不是追加（家族实测口径，例：`dsh-autotier/package.json` 的 `dshVersions` = `["0.1.2-rc.1", "0.1.5-rc.1"]`）。
