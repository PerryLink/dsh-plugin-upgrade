> 适用：任何 `@deepseek-ai/dsh-*` peer 落在 `>=0.1.2-rc.1 <0.2.0`、且需要同时支持 `0.1.5-rc.1` 的插件仓（含带 client 半边的仓）。

## 0. 这张卡是什么 · 怎么读

### 0.1 合并后的走廊

| 项 | 值 |
|---|---|
| 起点 | `0.1.3-alpha.1`（leg A 的 from 端） |
| 终点 | `0.1.5-rc.1`（leg B 的 to 端） |
| 两段 | leg A `0.1.3-alpha.1 → 0.1.5-alpha.1`；leg B `0.1.5-alpha.1 → 0.1.5-rc.1` |

为什么终点是 `0.1.5-rc.1` 而不是当前最新的 `0.1.5-rc.2`：harness 的 `0.1.5-rc.1 → 0.1.5-rc.2` 这一跳**没有新增面向插件的接缝**，所以本合并走廊按构造在 rc.1 收口；rc.2 只是同一适配结论上的版本号前进（本包的 dev/test 钉号与 CI 探针跑在 `0.1.5-rc.2` 线上，以便用最新已发布类型线验证同一份接缝目录）。**走廊不会因此变宽**：见 §0.4。

### 0.2 leg B 的 `C3` 已并入 `M1`

leg B 的旧卡把"本地门禁编译的是过期类型线"记作独立接缝 `C3`。它与 leg A 的 `M1` 是**同一条缺陷**（本地门禁编译的是过期类型线 → typecheck 静默回退、假绿），只是 leg A 记录了 (b) 因（`tsconfig` `paths` 指向不存在的 checkout 目录），leg B 补记了 (a) 因（dev/test 依赖钉在 `0.1.5-alpha.*` 行）。合并后只有 **`M1`** 一条接缝，两因同表；leg B 的原有叙述按此改写，并在原处保留"leg B 卡片原记作 `C3`"的说明。

### 0.3 怎么读

1. **先定位你的腿。** 按你仓库的 peer band / 目标宿主线选腿：目标 `0.1.5-alpha.1`、或 peer 低于 `0.1.5-alpha.1` ⇒ 读 **§1 Leg A**；目标 `0.1.5-rc.1`、或带 client 半边 ⇒ 读 **§2 Leg B**；从 `0.1.3-alpha.1` 一路升到 `0.1.5-rc.1` ⇒ 两条都读，先 A 后 B。
2. **再看 §3 合并接缝索引**：20 条 id、级别、一句话，是这份目录的唯一入口，也是 `lib/scan.mjs` 与 `test/card.test.mjs` 对齐的对象。
3. **两条腿各自保留原文。** §1 与 §2 是两张旧卡的**全文**（只做标题降级、leg B 的 `C3`→`M1` 改写，以及一段来源说明），因此其中的 `path:line` 证据、实测规模、裁定理由与边界声明都按原样保留；两条腿里提到的包名（`dsh-plugin-upgrade`、`dsh-plugin-upgrade-rc1`）与 CLI 名（`dsh-plugin-upgrade-scan`、`dsh-plugin-upgrade-rc1-scan`）都是**历史名**，合并后的包名与 CLI 见本页页首。
4. **编号是两条腿各自的历史编号**：leg A 用 `S1`–`S10`/`M1`，leg B 用 `C*`/`H*`/`P1`，合并后同属一份 20 条目录；leg B §2 里"编号刻意与姊妹包的 `S1`–`S10` / `M1` 错开"一句描述的是**合并前**的状态。

### 0.4 走廊永不加宽，但一个包可以承载多条**已封口**的走廊

- 合并的是**同一段 span 的两个连续 hop**，不是"任意版本都能升"：`0.1.5-rc.1` 之后的任何跳（含 `rc.2` 及正式版）若新增面向插件的接缝，仍按老规矩处理——**新走廊新包**，不往本卡上追加。
- 每条腿保留自己的**证据、卡片章节、夹具与回滚路径**：leg A 的证据在 §1 与 `docs/EVIDENCE.md` §A，leg B 的在 §2 与 `docs/EVIDENCE.md` §1–§10；`fixtures/leg-a-bad-repo` / `fixtures/leg-a-good-repo` 是 leg A 的夹具，`fixtures/bad-repo` / `fixtures/good-repo` 是 leg B 的。
- 因此本包**可以**共享一份 `SEAMS`（一个扫描器、一张目录），但两支的证据与回滚不互相依赖：任一腿的适配可以单独回滚。

### 0.5 本次合并的两条硬规则

1. **peer 区间保留两段**（`>=0.1.2-rc.1 <0.2.0 || >=0.1.5-alpha.1 <0.2.0`）：`P1` 明确禁止把它简化成单段（见 §2 §9）。本包自身的 `peerDependencies` 与 `dshWorkshop.compatibility.dshVersions` 都遵守这条。
2. **本地门禁是必要非充分**：先清 `M1` 与 `P1`（假绿与 peer 误改不排掉，后面全是幻觉），再谈其它；client 半边另需真实浏览器断言。

### 3. C1 · 裸 slot `conversation` 被删除（**本卡的中心接缝**）

### 3.1 上游事实（逐条实测）

同一文件同一位置，`packages/client/ui-conversation/src/client/apply.ts`：

```
dsh-v0.1.5-alpha.1:…/apply.ts:217:    name: 'conversation',
dsh-v0.1.5-rc.1:…/apply.ts:220:    name: 'main.conversation',

dsh-v0.1.5-rc.1:…/apply.ts:391:      key: 'conversation',

```

- 公开 slot 目录 `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` 的 `key:` 集合：alpha.1 = **57**，rc.1 = **61**。
- **删除（1 个）**：`conversation`。**新增（5 个）**：`main`、`main.conversation`、`rightbar.session`、`sidebar.panellist`、`sidebar.right.tab.document`。
- rc.1 全树搜 `name: 'conversation'`：只剩 `packages/client/ui-agent-preset/tests/apply.client.spec.ts:135` 一处**测试夹具残留**，实现侧零命中，**没有别名、没有 shim**。
- 精度：`conversation.input.left`、`conversation.session.header.actions`、`conversation.chat.node` 这些**以 `conversation.` 开头的名字本身没有变**，只有**裸 `conversation` 这一个 key** 被删除。`declaredBy` 的措辞从 `'an entry in conversation'` 变成 `'an entry in main.conversation'` 是目录描述文案。

### 3.2 失效形态是静默的（C1 必须保持 error 的理由）

rc.1 的公开 `ctx.slots` 契约（`packages/extensions/cordis-client-runner/src/client/api-catalog.ts`，`SERVICE_API` 的 `key: 'slots'`）逐字为：

> `inject(key: keyof SlotMap & string, callback: () => SlotInjectionEffect): () => void`
> "Install an effect for each declaration lifetime of a slot. The callback runs synchronously when the declaration already exists; otherwise it runs inside the declaring `register()` call after the declaration is committed."

`conversation` 在 rc.1 **永不 declaration**，所以回调**永不执行**：插件的 UI 悄悄消失，没有报错、没有日志、没有挂载失败。这与姊妹走廊最核心的洞察（`M1` 的"假绿"）是**同一类失效模式，只是从编译期搬到了运行期**。

### 3.3 本仓裁定：这是**公开扩展点的破坏性移除**，不是 owner 内部席位改名

研究稿把这留作开放问题（"公开扩展点"还是"内部席位"）。本仓采纳的裁定与理由：

**裁定：C1 是公开扩展点的破坏性移除，保持 `error` 级。**

1. `conversation` **确实出现在**两个 tag 都公开可查的 slot 目录（`slot-catalog.ts` → Inspect `Slots.listSubTree`）里，插件作者正是通过这份目录选 slot 的。
2. `ctx.slots.inject` 的公开契约明确支持"等 declaration 出现"的用法（§3.2 引文）。
3. 删除**没有别名**，rc.1 也未提供 shim 包；`conversation.` 前缀下的其它 key 全部保留，说明这不是一次体系化重命名，而是**单个 key 的移除**。
4. 上游在 `docs/` 里**没有**任何 deprecation 或 migration note：`docs/capability-seams.md` 的区间 diff 只新增了服务级 `ctx.sessionFeedback` 一行，**没有**任何 slot 级说明。**rc.1 至今没有发布这份迁移说明。**
5. 反向证据（研究稿提出的"内部席位"论据）成立但不改变结论：rc.1 的命名体系确实转向 `main.*` / `rightbar.session` 这类带父入口的点分名字。**这是动机，不是兼容性结论**——无论上游意图如何，第三方插件面对的都是"目标 key 消失 + 无别名 + 无 deprecation + 静默失效"。

**因此本卡给出完整改写配方（§3.4），并要求对每个 `C1` 命中项做真实浏览器断言（§10 第 5 步）。** 静态扫描与 `typecheck` 都不能作为 C1 已修好的证据。

### 9. P1 · peer 区间（**最容易"顺手简化"而踩雷的一行**）

用 semver **7.8.5** 实测（`satisfies('0.1.5-rc.1', range)`）：

| 区间 | `0.1.5-rc.1` 是否满足 |
|---|---|
| `>=0.1.2-rc.1 <0.2.0`（**砍掉第二段**） | **false** ❌ |
| `>=0.1.2-rc.1 <0.2.0 \|\| >=0.1.5-alpha.1 <0.2.0`（家族现行） | **true** ✅ |
| `>=0.1.5-alpha.1 <0.2.0` | **true** ✅（`0.1.5-alpha.1` 自身也 true） |

原因：npm semver 的 **prerelease-tuple 规则**——带 prerelease 的版本只有在同一 `[major,minor,patch]` 元组上**至少有一个带 prerelease 的 comparator** 时才被允许满足该集合。`>=0.1.2-rc.1` 的元组是 `0.1.2`，管不到 `0.1.5-rc.1` 的元组 `0.1.5`，于是整条被拒；第二段 `>=0.1.5-alpha.1` 的元组正是 `0.1.5` 且带 prerelease，才把它放行。

这与工作区已记录的历史事故同源（旧范围 `>=0.1.0-rc.8 <0.2.0` 因同一规则在裸解析下只匹配 `0.1.0-rc.8` 一行）。

**硬规则：rc.1 适配不改 peer 区间；绝对不要把两段"或"合并成一段。** 需要区分两件事：

- **peer 区间不动** —— 这是 `dsh-skill` 等依赖解析用的。
- **`dshWorkshop.compatibility.dshVersions` 换号** —— 市场/工坊的兼容声明：把 `0.1.5-alpha.1` **替换**为 `0.1.5-rc.1`，不是追加（家族实测口径，例：`dsh-autotier/package.json` 的 `dshVersions` = `["0.1.2-rc.1", "0.1.5-rc.1"]`）。

### 10. 强制验证顺序（本地门禁是必要非充分）

1. `dsh-plugin-upgrade-rc1-scan --repo <仓库>` 出 `file:line` 事实。**先看 `M1` 与 `P1`**：假绿与 peer 误改不排掉，后面全是幻觉。

### 12. 剩余风险与边界（诚实声明）

1. **家族侧是潜在破坏（latent），不是实际破坏。** 2026-09-10 实测：家族 15 个仓的生产代码共只用 **8** 个 slot key —— `conversation.input.left`、`conversation.session.header.actions`、`settings.plugin.item`、`settings.plugins.tab`、`settings.section`、`shell.overlay`、`sidebar.footer.action`、`tool.call.toolview` —— 删除集只有 `conversation` 一个元素，所以这 8 个**全部存活**；全仓搜 `inject('conversation'` / `name: 'conversation'` / `sidebar-textpreview` = **零命中**。这正是 37 个仓的 rc.1 CHANGELOG 条目全是 pin-only（`dsh-autotier/CHANGELOG.md:14`、`dsh-mcp-panel/CHANGELOG.md:16`、`dsh-plugin-guide/CHANGELOG.md:22`、`dsh-permission-rules/CHANGELOG.md:69`，措辞逐字相同）的原因。（先前研究稿记为 9 个 key：多出的 `conversation.chat.node` 在本工作区只出现在 `dsh-plugin-guide/references/official-docs/` 的官方文档快照里，不是任何家族仓的代码。）
   **不要把这跳说成"家族已被破坏"**：家族今天不中招，是因为它的 client 半边恰好只用了安全 key，而**不是**因为 rc.1 兼容 alpha.1。社区第三方的 client 插件完全可能命中 `C1`/`C2`。
2. **上游未发布 rc.1 的迁移说明。** 本卡的接缝是我方从 tag 区间 diff、公开 slot 目录与公开 service 目录推导的，不是上游声明的；`conversation` 的删除**没有任何 deprecation 记录**。若上游随后发布官方说明，卡片应以官方为准并重排严重级别。
3. **C1 的裁定是本仓的判断**（§3.3），不是上游声明。
4. **L9（浏览器）未执行。** 本卡与扫描器都是静态/契约级证据；`C1`/`C2`/`C5`/`H2` 的运行期结论必须在真实页面复验（§10 第 5 步）。L11（真实模型）同样未执行。
5. **扫描器是启发式。** `C4`/`C5`/`H1`/`H2`/`H4` 是线索级；`H3` 刻意不检测。error 级的 `C1`/`C2`/`M1`/`P1` 已在合成夹具 + 真实仓双向验证。
6. **未验证**：`0.1.5-alpha.2` 是否被任何家族仓钉过（本卡只从 tag 存在性与 commit 数推断其为短命 tag，未逐仓核验 devDeps 历史）。
7. **未验证**：除 slot 目录与已列出的服务之外，`packages/client/*` 是否还存在面向插件作者、未被公开目录收录的破坏面。
